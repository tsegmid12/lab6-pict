## 2. A — Category-Partition

### A1. Category болон сонголтуудыг тодорхойлох

Мөнгө шилжүүлэх үйлдлийн үндсэн оролтууд болон орчны нөхцөлийг дараах category-уудаар тодорхойлов.

| Category | Сонголт | Тайлбар |
|---|---|---|
| From | Valid | Идэвхтэй, шилжүүлэг хийх боломжтой данс |
| From | Frozen | Царцаасан данс |
| From | Missing | Системд байхгүй данс |
| To | Valid | Байгаа, өөр данс |
| To | Missing | Системд байхгүй хүлээн авагч |
| To | SameAsFrom | Илгээгчтэй ижил данс |
| Amount | Normal | Энгийн зөв дүн |
| Amount | Zero | 0 дүн |
| Amount | Negative | Сөрөг дүн |
| Amount | OverBalance | Дансны үлдэгдлээс их дүн |
| Amount | OverLimit | Өдрийн лимитээс их дүн |
| Currency | Same | Дансны валюттай ижил |
| Currency | Different | Дансны валютаас өөр |
| DailyUsed | None | Өдрийн лимитээс өмнө ашиглаагүй |
| DailyUsed | Partial | Өдрийн лимитийн тодорхой хэсгийг ашигласан |

**Category сонгосон үндэслэл:**

- `From` нь шилжүүлэг эхлүүлэх дансны төлөвийг шалгана.
- `To` нь хүлээн авагчийн данс зөв эсэх болон өөрийн данс руу шилжүүлэх оролдлогыг шалгана.
- `Amount` нь зөв дүн, тэг, сөрөг, үлдэгдэл болон лимитээс хэтэрсэн нөхцөлүүдийг хамарна.
- `Currency` нь ижил болон өөр валюттай шилжүүлгийг ялгана.
- `DailyUsed` нь өдрийн лимитийн ашиглалтаас хамаарах орчны нөхцөлийг илэрхийлнэ.

### A2. Хязгаарлалт болон хүчинтэй комбинацийн тооцоо

`transfer.model` файлд дараах гурван IF constraint тодорхойлсон.

```text
IF [From] <> "Valid" THEN [Amount] = "Normal";
IF [To] <> "Valid" THEN [Amount] = "Normal";
IF [Amount] = "OverLimit" THEN [DailyUsed] = "Partial";
```

Эдгээр нөхцөлийн утга:

| Constraint | Тайлбар |
|---|---|
| From ≠ Valid → Amount = Normal | Илгээгчийн данс хүчинтэй биш үед Amount-ийг Normal байлгана |
| To ≠ Valid → Amount = Normal | Хүлээн авагчийн данс хүчинтэй биш үед Amount-ийг Normal байлгана |
| Amount = OverLimit → DailyUsed = Partial | Өдрийн лимитээс хэтэрсэн дүнг шалгах үед DailyUsed = Partial байна |

**Бүрэн комбинацийн тооцоо**

`transfer.model` файлд:

- From — 3 утга
- To — 3 утга
- Amount — 5 утга
- Currency — 2 утга
- DailyUsed — 2 утга

Constraint хэрэгжүүлэхээс өмнөх нийт боломжит комбинаци:

`3 × 3 × 5 × 2 × 2 = 180`

IF constraint-үүдийг хэрэгжүүлсний дараах хүчинтэй комбинацийн тооцоо:

1. From = Frozen эсвэл Missing үед Amount = Normal:

`2 × 3 × 1 × 2 × 2 = 24`

2. From = Valid, To = Missing эсвэл SameAsFrom үед Amount = Normal:

`1 × 2 × 1 × 2 × 2 = 8`

3. From = Valid, To = Valid үед Amount-ийн бүх утгыг ашиглана. OverLimit үед DailyUsed = Partial байх тул:

`1 × 1 × (4 × 2 + 1 × 1) × 2 = 18`

Нийт хүчинтэй комбинаци:

`24 + 8 + 18 = 50`

Иймээс `transfer.model`-ийн IF constraint-үүдийн дараа 180 боломжит комбинациас 50 хүчинтэй комбинаци үлдэнэ.

> 50 нь model-ийн constraint-үүдийн дараах хүчинтэй бүх комбинацийн тоо юм. Энэ нь PICT-ийн pairwise covering array-аар үүсгэсэн тестийн мөрийн тоо биш.

**Анхаарах зүйл:** Frozen, Missing, SameAsFrom, Zero, Negative, OverBalance зэрэг нь тестээр шалгах бизнесийн алдаатай нөхцөлүүд юм. Эдгээрийг бүгдийг нь model-оос хассан гэсэн үг биш. Одоогийн IF constraint-үүд зөвхөн Amount болон DailyUsed-ийн зарим хослолыг хязгаарлаж байна.

### A3. Спецификацийн тестийн хүснэгт

Category-Partition аргаар дараах гараар тодорхойлсон тест кейсүүдийг боловсруулав.

| ID | From | To | Amount | Currency | DailyUsed | Хүлээгдэх үр дүн |
|---|---|---|---|---|---|---|
| A01 | Valid | Valid | Normal | Same | None | Амжилттай шилжүүлэг |
| A02 | Frozen | Valid | Normal | Same | None | Илгээгч царцаасан алдаа |
| A03 | Missing | Valid | Normal | Same | None | Илгээгчийн данс олдохгүй |
| A04 | Valid | Missing | Normal | Same | None | Хүлээн авагч олдохгүй |
| A05 | Valid | SameAsFrom | Normal | Same | None | Ижил дансны алдаа |
| A06 | Valid | Valid | Zero | Same | None | Дүн тэг байх алдаа |
| A07 | Valid | Valid | Negative | Same | None | Сөрөг дүнгийн алдаа |
| A08 | Valid | Valid | OverBalance | Same | None | Үлдэгдэл хүрэлцэхгүй |
| A09 | Valid | Valid | OverLimit | Same | Partial | Өдрийн лимит хэтэрсэн |
| A10 | Valid | Valid | EqualBalance | Same | None | Үлдэгдэлтэй тэнцүү дүнгийн boundary |
| A11 | Valid | Valid | EqualLimit | Same | Partial | Лимиттэй тэнцүү дүнгийн boundary |
| A12 | Valid | Valid | Normal | Different | None | Валют хөрвүүлэлттэй шилжүүлэг |
| A13 | Missing | Missing | Zero | Same | None | From алдааны давуу эрэмбэ |

**Тайлбар:** A10 болон A11 нь гараар тодорхойлсон нэмэлт boundary тестүүд юм. `transfer.model`-ийн Amount category-д `EqualBalance`, `EqualLimit` утгууд одоогоор байхгүй тул эдгээр нь одоогийн PICT model-оос автоматаар үүссэн тест биш.

Олон алдаа зэрэг үүссэн тохиолдолд `From → To → Amount` гэсэн шалгах дарааллыг ашиглан аль алдаа түрүүлж илрэхийг тодорхойлов.

## 3. B — PICT ашиглан Combinatorial Testing хийх

### B1. Browser model — 2-way болон 3-way testing

Browser-ийн тохиргооны параметрүүдийг `browser.model` файлд тодорхойлж, PICT ашиглан 2-way болон 3-way covering array үүсгэв.

Browser model-ийн параметрүүд:

- Content: Allow, Restrict, Block
- Cookies: Allow, Restrict, Block
- Popups: Yes, No
- Addons: Yes, No
- Attacks: Yes, No
- Forgeries: Yes, No

Бүрэн комбинацийн тоо:

`3 × 3 × 2 × 2 × 2 × 2 = 144`

| Тестийн төрөл | Бүрэн комбинаци | PICT-ийн үүсгэсэн мөр |
|---|---:|---:|
| 2-way | 144 | 10 |
| 3-way | 144 | 20 |

2-way testing нь параметрүүдийн бүх боломжит хос утгын хослолыг хамруулах зорилготой.

3-way testing нь гурван параметрийн бүх боломжит утгын хослолыг хамруулах зорилготой.

PICT-ийн greedy алгоритм нь шаардлагатай хамралтыг хангах тестийн мөрүүдийг үүсгэдэг. Гэхдээ хамгийн цөөн мөрийн оптимумыг заавал олно гэсэн баталгаа биш.

Үр дүнгийн файлууд:

- `results/browser-2way.txt`
- `results/browser-3way.txt`

### B2. Transfer model-уудын үр дүнгийн харьцуулалт

Мөнгө шилжүүлэх үйлдлийн хувьд гурван өөр PICT model үүсгэн, constraint болон negative testing-ийн нөлөөг харьцуулав.

**Happy Path шалгуур:**

- From = Valid
- To = Valid
- Amount = Normal

| Үр дүнгийн файл | Арга | Нийт мөр | Happy Path | Бусад мөр |
|---|---|---:|---:|---:|
| `transfer-nc.txt` | IF constraint ашиглаагүй | 17 | 0 | 17 |
| `transfer.txt` | IF constraint ашигласан | 16 | 0 | 16 |
| `transfer-neg.txt` | Negative testing (`~`) | 30 | 5 | 25 |

**Үр дүнгийн тайлбар:**

Эдгээр model-ийн параметрүүд бүрэн ижил биш тул мөрийн тооны ялгааг зөвхөн IF constraint-ийн нөлөө гэж дүгнэхгүй.

Үр дүнгийн файлууд:

- Амжилттай шилжүүлгийн үед илгээгчийн үлдэгдэл буурч, хүлээн авагчийн үлдэгдэл нэмэгдэх.

**Бодит API баталгаажуулалтын төлөв:**

Энэ README-д T01–T03-ийн Oracle-ийг хүлээгдэж буй үр дүн байдлаар тодорхойлсон. Postman-аар бодит API хүсэлт илгээж, HTTP status, response body болон дансны үлдэгдлийн өөрчлөлтийг шалгаж нотлох шаардлагатай. Бодит хариуг шалгаагүй тул тодорхой status code, response JSON болон үлдэгдлийн утгыг зохиомлоор бичээгүй.

**3. Дүгнэлт**

Гараар тодорхойлсон A3 болон PICT-ээр үүсгэсэн тестүүд нь өөр өөр давуу талтай.

A3 нь бизнесийн шаардлагад үндэслэн Happy Path, сөрөг нөхцөл болон boundary утгуудыг зориудаар сонгож, хүлээгдэх үр дүнг тодорхойлох боломж олгодог.

Харин PICT нь олон параметрийн хослолыг системтэй үүсгэж, гараар сонгоход орхигдож болох хослолуудыг хамруулахад тусалдаг.

Харьцуулалтаас харахад PICT-ийн сонгосон B3 гурван тест нь A3-ийн амжилттай шилжүүлэг, сөрөг дүн, царцаасан дансны нөхцөлүүдтэй давхцаж байна. Гэхдээ EqualBalance болон EqualLimit зэрэг boundary нөхцөлүүдийг B3-ийн сонгосон гурван мөр дангаараа хамрахгүй.

Иймээс Category-Partition болон PICT аргыг хамтад нь ашиглах нь үр дүнтэй. Category-Partition нь чухал бизнес дүрэм, boundary нөхцөлийг тодорхойлж, PICT нь параметрүүдийн хослолын хамралтыг нэмэгдүүлнэ.

## 4. Дүгнэлт

Энэхүү лабораторийн ажлаар Category-Partition аргаар мөнгө шилжүүлэх үйлдлийн тестийн category болон сонголтуудыг тодорхойлж, PICT ашиглан pairwise болон 3-way тестийн хувилбарууд үүсгэв.

Browser model-ийн хувьд 2-way testing-ээр 10, 3-way testing-ээр 20 мөр үүсгэсэн. Transfer model-уудын хувьд constraint-гүй, constraint-тэй болон negative testing аргуудыг харьцуулсан.

Мөн PICT-ийн бодит мөрүүдээс гурван тест кейс сонгон, Oracle буюу хүлээгдэж буй үр дүнг тодорхойлов. Бодит API-ийн Oracle баталгаажуулалтыг Postman-аар хийж, хүсэлтийн болон хариуны нотолгоог нэмэх шаардлагатай.

Энэ ажлаас Category-Partition болон Combinatorial Testing аргуудыг хамтад нь ашигласнаар бизнесийн чухал нөхцөлүүд болон олон параметрийн хослолыг илүү системтэй тестлэх боломжтойг ойлгож авлаа.
