## 2. A — Category-Partition

### A1. Category болон сонголтуудыг тодорхойлох

Мөнгө шилжүүлэх үйлдлийн үндсэн оролтууд болон орчны нөхцөлийг дараах category-уудаар тодорхойлов.

| Category | Сонголт | Тайлбар |
|---|---|---|
| From | Valid | Идэвхтэй, шилжүүлэг хийх боломжтой данс |
| From | Frozen | Царцаасан данс |
| From | Missing | Системд байхгүй данс |
| To | Valid | Байгаа, өөр данс |
| To | Missing | Системд байхгүй хүлээн авагч |
| To | SameAsFrom | Илгээгчтэй ижил данс |
| Amount | Normal | Энгийн зөв дүн |
| Amount | EqualBalance | Дансны үлдэгдэлтэй яг тэнцүү дүн |
| Amount | EqualLimit | Өдрийн үлдсэн лимиттэй яг тэнцүү дүн |
| Amount | Zero | 0 дүн |
| Amount | Negative | Сөрөг дүн |
| Amount | OverBalance | Дансны үлдэгдлээс их дүн |
| Amount | OverLimit | Өдрийн үлдсэн лимитээс их дүн |
| Currency | Same | Дансны валюттай ижил |
| Currency | Different | Дансны валютаас өөр |
| DailyUsed | None | Өдрийн лимитээс өмнө ашиглаагүй |
| DailyUsed | Partial | Өдрийн лимитийн тодорхой хэсгийг ашигласан |

**Category сонгосон үндэслэл:**

- `From` нь шилжүүлэг эхлүүлэх дансны төлөвийг шалгана.
- `To` нь хүлээн авагчийн данс зөв эсэх болон өөртэйгөө шилжүүлэг хийх нөхцөлийг шалгана.
- `Amount` нь энгийн, сөрөг, тэг, үлдэгдэл болон лимитийн заагийн нөхцөлийг хамарна.
- `Currency` нь ижил болон өөр валюттай шилжүүлгийг ялгана.
- `DailyUsed` нь хүсэлтийн body-д шууд дамжуулагдахгүй байж болох боловч өдрийн лимитийн үлдэгдлийг тодорхойлох орчны нөхцөл юм.

### A2. Хязгаарлалт болон хүчинтэй комбинацийн тооцоо

Тестийн загварт бодит бус нөхцөл үүсэхээс сэргийлж дараах дүрмүүдийг тодорхойлов.

| Нөхцөл | Хязгаарлалт | Үндэслэл |
|---|---|---|
| From = Frozen | `[ERROR]` | Илгээгч царцаасан данстай |
| From = Missing | `[ERROR]` | Илгээгчийн данс байхгүй |
| To = Missing | `[ERROR]` | Хүлээн авагчийн данс байхгүй |
| To = SameAsFrom | `[ERROR]` | Өөрийн данс руу шилжүүлэг хийх боломжгүй |
| Amount = Zero | `[ERROR]` | Шилжүүлгийн дүн тэг байж болохгүй |
| Amount = Negative | `[ERROR]` | Шилжүүлгийн дүн сөрөг байж болохгүй |
| Amount = OverBalance | `[ERROR]` | Үлдэгдлээс их дүн шилжүүлэх боломжгүй |
| Amount = OverLimit | `[ERROR]` | Өдрийн лимитээс хэтэрсэн |
| Amount = EqualBalance | `[SINGLE]`, `[IF]` | Үлдэгдэлтэй яг тэнцүү дүнгийн boundary нөхцөл |
| Amount = EqualLimit | `[SINGLE]`, `[IF]` | Өдрийн лимитийн яг заагийн boundary нөхцөл |

Хэрэглэсэн IF нөхцөлүүд:

- From буруу үед Amount-ийг Normal байлгана.
- To буруу үед Amount-ийг Normal байлгана.
- EqualBalance үед Currency = Same, DailyUsed = None байна.
- EqualLimit үед Currency = Same, DailyUsed = Partial байна.
- OverLimit үед DailyUsed = Partial байна.

**Бүрэн комбинацийн тооцоо:**

Хязгаарлалт хэрэгжүүлэхээс өмнөх боломжит комбинаци:

`3 × 3 × 7 × 2 × 2 = 252`

IF нөхцөлүүдийг хэрэгжүүлсний дараах хүчинтэй комбинаци:

- From = Frozen эсвэл Missing үед: 8
- From = Valid, To = Missing эсвэл SameAsFrom үед: 8
- From = Valid, To = Valid үед: 20

Нийт:

`8 + 8 + 20 = 36`

Ингэснээр 252 боломжит комбинациас 36 хүчинтэй комбинаци үлдэнэ.

> 36 нь IF нөхцөлүүдийн дараах хүчинтэй бүх комбинацийн тоо юм. Энэ нь PICT-ийн covering array-аас гарсан тестийн мөрийн тоотой ижил ойлголт биш.

## 3. B — PICT ашиглан Combinatorial Testing хийх

### B1. Browser model — 2-way болон 3-way testing

Browser-ийн тохиргооны параметрүүдийг `browser.model` файлд тодорхойлж, PICT ашиглан 2-way болон 3-way covering array үүсгэв.

| Тестийн төрөл | Бүрэн комбинаци | PICT-ийн мөрийн тоо |
|---|---:|---:|
| 2-way | 144 | 10 |
| 3-way | 144 | 20 |

2-way testing нь параметрүүдийн бүх хос утгын хослолыг хамруулах зорилготой.

3-way testing нь гурван параметрийн бүх боломжит утгын хослолыг хамруулах зорилготой.

PICT-ийн greedy алгоритм нь хамралтыг хангах тестийн мөрүүдийг үүсгэдэг боловч хамгийн цөөн мөрийн оптимумыг заавал олно гэсэн баталгаа биш.

Үр дүнгийн файлууд:

- `results/browser-2way.txt`
- `results/browser-3way.txt`

### B2. Transfer model-уудын үр дүнгийн харьцуулалт

Мөнгө шилжүүлэх үйлдлийн хувьд гурван өөр PICT model үүсгэн, constraint болон negative testing-ийн нөлөөг харьцуулав.

**Happy Path шалгуур:**

- From = Valid
- To = Valid

| Үр дүнгийн файл | Арга | Нийт мөр | Happy Path | Бусад мөр |
|---|---|---:|---:|---:|
| `transfer-nc.txt` | IF constraint ашиглаагүй | 17 | 0 | 17 |
| `transfer.txt` | IF constraint ашигласан | 16 | 0 | 16 |
| `transfer-neg.txt` | Negative testing (`~`) | 30 | 5 | 25 |

**Үр дүнгийн тайлбар:**

1. `transfer-nc.model` нь нэмэлт IF хязгаарлалтгүйгээр тестийн хувилбарууд үүсгэсэн.
2. `transfer.model` нь IF нөхцөлөөр бодит бус комбинациудыг хязгаарласан.
3. `transfer-neg.model` нь `~` тэмдэглэгээг ашиглан сөрөг тестийн нөхцөлүүдийг үүсгэсэн.
4. `transfer-neg.txt` файлд 5 Happy Path, 25 бусад тестийн мөр байна.

Эдгээр model-ийн параметрүүд бүрэн ижил биш тул мөрийн тооны ялгааг зөвхөн IF constraint-ийн нөлөө гэж дүгнэхгүй.

Үр дүнгийн файлууд:

A3 хэсэгт Category-Partition аргаар гараар тодорхойлсон тест кейсүүдийг B2 хэсгийн PICT үр дүнгээс сонгосон тест кейсүүдтэй харьцуулав.

#### 3. Дүгнэлт

Гараар тодорхойлсон A3 болон PICT-ээр үүсгэсэн тестүүд нь өөр өөр давуу талтай.

A3 нь бизнесийн шаардлагад үндэслэн Happy Path, сөрөг нөхцөл болон boundary утгуудыг зориудаар сонгож, хүлээгдэх үр дүнг тодорхойлох боломж олгодог.

Харин PICT нь олон параметрийн хослолыг системтэй үүсгэж, гараар сонгоход орхигдож болох хослолуудыг хамруулахад тусалдаг.

Харьцуулалтаас харахад PICT-ийн сонгосон B3 гурван тест нь A3-ийн амжилттай шилжүүлэг, сөрөг дүн, царцаасан дансны нөхцөлүүдтэй давхцаж байна. Гэхдээ EqualBalance болон EqualLimit зэрэг boundary нөхцөлүүдийг B3-ийн сонгосон гурван мөр дангаараа хамрахгүй.

Иймээс Category-Partition болон PICT аргыг хамтад нь ашиглах нь илүү үр дүнтэй. Category-Partition нь чухал бизнес дүрэм, boundary нөхцөлийг тодорхойлж, PICT нь параметрүүдийн хослолын хамралтыг нэмэгдүүлнэ.
